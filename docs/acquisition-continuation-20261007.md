# 100ペア取得の継続運用

2026-10-07のユーザー指示に基づく。目的は正しく取得・評価した100論理ペア。
途中のRelease公開は取得条件ではない。全体の公開用データは取得後にまとめる。

- 既存の割当、評価版、モデル、2ペア/4 Run並列、Use balance OFF、有料fallbackなし、
  累積使用量と予算を継承する。低品質・生成プログラムの失敗は有効な観測として保持する。
- 技術障害では保存済み生成物の評価を先に試す。回復不能な技術障害の証拠がある場合、
  送信・使用量に不確定性が残ることだけで再試行を禁止しない。不確定性も原本も残す。
  新しい復旧記録には版付きretry_policyを保存し、過去の保留判定には適用しない。
  不明な原因や低品質だけを再取得理由にしない。
- 再試行は新しいepoch/Run UUIDを使用し、異なる試行のarmを合成しない。
- 所有プロセスの停止、生成物の対応、アーカイブ検証、評価の成立を確認して採用する。
  公開処理は呼ばない。旧データ・STOP・計画・評価を上書きしない。

運転コードは`tools/acquisition/driver.py`と`owner.py`。`S2_SUMMARY`で現在の計画の
summaryを明示する。ownerの`--status`は台帳から状態を作り直す。`LABEL --resume WAVE`
は予約済みのwaveを再送せず締める。driverは起動時に未完了waveを回収し、終了時の
例外についても一度保存済みwaveから復旧する。復旧不能時は原因を残して終了する。
実行中のheartbeatと停止ログは外部の監督から確認する。

引退済みの変更しない履歴は、1回の操作で検証した結果を、その操作内の兄弟呼出しにも
再利用する。操作をまたぐキャッシュは作らない。次の操作では原本の変更・STOP・使用量を
再検証する。現行waveの起動条件・所有資源・使用量上限・評価とアーカイブの確認は維持する。
状態表示のためだけに全履歴検証を重ねない。

通常締め処理の試験は実際のアーカイブ・完了receipt・採用台帳・検証処理を通す。
中断後の再開と再実行で二重採用しないこと、品質0でも採用することを検証する。
ローカル試験に加えて、実モデルの取得・評価・保存・次waveへの遷移を確認する。
