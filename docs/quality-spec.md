## 4. 試験条件

### 4.1 初期状態

- 評価ごとに**空の作業ディレクトリ**と**空の SQLite ファイル**を与える。前の評価の DB を再利用しない。
  作業ディレクトリが空でない場合、評価器は**採点せず**評価側の障害として記録する（[evaluator.md](evaluator.md) §3）。
  引き継ぐと、2 回目の採点で注文が前回の分と合わせて数えられ、この初期条件が崩れるためである。
- アプリは `ConnectionStrings__MusicStoreEntities=Data Source=<評価専用パス>` と `--urls http://127.0.0.1:<動的ポート>` で起動する。
- 評価器は**入力の成果物を書き換えない**。発行は作業ディレクトリへ複製したソースに対して行う。
  成果物を直接発行すると、`dotnet publish` が `obj/` `bin/` を成果物の中に書き、
  **採点した成果物と固定した成果物が別物になる**（[evaluator.md](evaluator.md) §3）。
- 初期カタログはアプリの初回起動時に投入される（評価器は投入を行わない）。
- 起動待ちは `GET /` が 200 を返すまで（上限 60 秒）。上限超過は**評価側障害**とする。

### 4.5 維持する表示契約

旧実装の JavaScript が依存している識別子、および金額の書式は**外部契約として維持する**。これらは検査の観測点であり、見た目の指定ではない。

| 対象 | 契約 | 由来 |
| --- | --- | --- |
| 金額 | `0.00` 形式（小数点は `.`、小数 2 桁） | 検査を決定的にするための課題側の判断 |
| かご明細行 | `<tr id="row-{明細ID}">` | 旧 `Views/ShoppingCart/Index.cshtml` の AJAX |
| かご明細の数量 | `<td id="item-count-{明細ID}">N</td>` | 同上 |
| かご明細の削除リンク | `class="RemoveLink" data-id="{明細ID}"` | 同上 |
| かご合計 | `<td id="cart-total">金額</td>` | 同上 |
| かご件数 | レイアウト内に `id="cart-status"` で `Cart (N)` | 旧 `Views/ShoppingCart/CartSummary.cshtml` |
| ジャンル別一覧のアルバムリンク | `href="/Store/Details/{アルバムID}"` | 旧 `Views/Store/Browse.cshtml` |
| 削除要求の応答 | JSON オブジェクト（`ItemCount` `DeleteId` `CartTotal` `CartCount` `Message`） | 旧 `Views/ShoppingCart/Index.cshtml` が読む項目 |
| 完了画面 | 本文に注文番号 | 旧 `Views/Checkout/Complete.cshtml` |

`data-id` が指すのは**かご明細の識別子**であり、アルバム ID ではない（旧実装の `Cart.RecordId` に対応）。

### 4.5.1 保存契約（`R-005` の観測点）

`R-005`（再起動でデータを失わない）は HTTP の応答だけでは観測できない。かごの帰属はセッションに紐づく識別子で判定されるため（`R-025`）、再起動でセッションが失われると、再起動前の注文は**どの HTTP 応答にも現れない**。そこで評価器は保存先を直接、**読み取り専用で**観測する。

| 項目 | 契約 |
| --- | --- |
| 保存先 | 起動構成の `ConnectionStrings__MusicStoreEntities` が指す SQLite ファイル |
| 注文表 | `Orders` |
| 注文番号の列 | `OrderId`（整数、重複しない。主キーであること） |
| 注文番号の値 | 完了画面に出る注文番号と同じ値 |
| 観測の方法 | 評価器が `SELECT COUNT(*) FROM Orders WHERE OrderId = ?` を読み取り専用で実行する。書き込み・スキーマ変更はしない |

評価器は次の順で観測する。

1. 注文確定の直後、**再起動する前**に、確定した注文番号の行が `Orders` にあることを確認する。
2. 同じ保存先のまま再起動し、**新しい注文を作る前に**、同じ注文番号の行がまだあることを確認する。
3. そのうえで新しい注文を作り、注文番号が変わることを確認する。

判定は次のように分ける。

| 観測したこと | 扱い |
| --- | --- |
| 再起動後にも同じ注文行がある | 保持を確認できた |
| 再起動前に注文行があるのに、再起動後に無い | **保持の失敗**。`R-005` を不合格にする |
| `Orders` 表・`OrderId` 列が無い、または SQLite ファイルが無い | **保存契約違反**。`R-005` を不合格にする |
| 評価側の事情で読めない（SQLITE_BUSY 等） | **判定不能**。`R-005` を `error` にし、成果物の欠陥と取り違えない |
| 再起動前の注文番号が得られない | 保持を確認できていない。合格にしない |

この契約は**本改訂で追加した**ものであり、公開前に提出された成果物へ遡って適用しない。追加の理由と影響は [decision-log.md](decision-log.md) に記録している。

`R-005` が確認するのは**注文行が残っていること**だけである。注文の金額・住所・明細の内容が保持されていることは確認していない（§2.1）。

### 4.6 許される非決定的な差異

次は判定に影響させない。

- 明細行の表示順、HTML の空白・属性順・改行、要素の追加（`<script>` `<link>` 等）
- **属性の書き方の流儀**。属性値の引用符は `"` でも `'` でもよく、`=` の前後の空白・タブ・改行、属性の順序も判定に影響させない（§4.5 の契約は識別子と値を定めており、表記を定めていない）
- アルバムアートの URL と画像の有無
- セッション ID、注文 ID、かご明細 ID の**値そのもの**（注文 ID は完了画面のリダイレクト先から取得する。連番であることを仮定しない）
- 追加の HTML ページ、追加のルート、追加の API
- ログ出力、標準出力の内容
- レスポンスの `Content-Type` の細かな差異（本文の解析は文字列照合で行う）
- 名前空間・アセンブリ名に `MvcMusicStore` のような旧名称を使うこと（`R-029` は旧実装の成果物・旧ホスト・旧フレームワークを見る）

属性の表記差を許容することと、値を取り違えることは別である。表記が同じでも、数量・金額・識別子の値が誤っていれば不合格にする（§4.7）。

### 4.7 正規化してはならない差異

- 金額の桁・丸め（`R-013` `R-016` `R-019` は完全一致で比較する）
- ジャンル別のアルバム件数（`R-003` は完全一致で比較する）
- 数量・金額・識別子の**値**（`R-011`〜`R-016` は属性の表記ではなく値を比較する）
- HTTP ステータスコード（`R-007` `R-009` は 404 であることを要求する）
- 旧実装を呼び出しているかどうか（`R-029`）

## 5. 判定と根拠

### 5.1 判定の単位

- 判定の単位は**要件**（`R-0xx`）。1 つの要件は 1 つ以上の**検査**（`C-0xx`）を持ち、**すべての検査が合格したとき**にその要件を合格とする。
- 検査は「入力・期待・観測・判定・証拠」を 1 行ずつ返す。証拠（観測した値、HTTP ステータス、抜粋）を必ず添える。

### 5.2 状態

| 状態 | 意味 |
| --- | --- |
| `pass` | 観測が期待に一致した |
| `fail` | 観測が期待に反した（**成果物の不具合**） |
| `blocked` | 前提が成立せず判定できない（例: 起動しないため閲覧系を判定できない） |
| `error` | 検査中に評価側の障害が起きた（例: 応答の解析に失敗、プロセスが異常終了） |

- **`blocked` と `error` を `pass` に変換しない。未評価を 0 点や合格に変換しない。**
- `blocked` は分母から外さない（未達として数える）。
- いずれかの検査が `error` のとき、**評価全体を `error`（品質不明）とし、品質点を返さない**。`null` を 0 に置き換えない。
- 品質点は「合格した要件数 ÷ 台帳の全要件数 × 100」とする。**未評価の要件を分母から落とさない。**

### 5.3 重大違反の扱い

`severity = critical` の要件（`R-001` `R-002` `R-005` `R-012` `R-013` `R-018` `R-022` `R-026` `R-027`）が 1 つでも不合格なら、**平均点に関係なく全体判定を `fail_critical`** とする。重大違反を単純な平均点に埋めない。

### 5.4 全体判定

| 全体判定 | 条件 |
| --- | --- |
| `pass` | すべての要件が `pass` |
| `fail_critical` | `severity = critical` の要件に `fail` がある |
| `fail` | 上記以外に `fail` がある |
| `blocked` | `fail` がなく、起動不能などで判定できない要件がある |
| `error` | 評価側の障害があり、品質を判定できない |

### 5.5 記録の形式

評価器は次を返す（[evaluator.md](evaluator.md) §6）。

| 出力 | 内容 |
| --- | --- |
| `evaluation.json` | 評価 ID、課題 ID、評価版、成果物ハッシュ、全体判定、品質点（または `null`）、要件別判定、未検査範囲、評価側障害 |
| `results.jsonl` | 検査ごとに 1 行。要件 ID、検査 ID、入力、期待、観測、判定、証拠 |
| `evidence/` | 生の HTTP 応答の抜粋とプロセスのログ |
| `evaluator-manifest.json` | 評価器の版、仕様台帳のハッシュ、成果物のハッシュ |

- **品質判定にトークン量を混ぜない。** トークン量は外側（`outer/`）の記録であり、本評価器は扱わない。
- 再採点は新しい評価 ID を発行し、以前の評価履歴を上書きしない（要件 §6）。

## 6. 再採点と評価履歴

- 同じ成果物を再採点すると、**新しい評価 ID** が発行され、以前の評価は [`inner/calibration/`](../inner/calibration/) に残す。
- 評価版（評価器・仕様台帳）が変わった場合も別の評価履歴として残す。評価 ID は `{課題ID}-{成果物ハッシュ先頭 12 桁}-{評価版}-{連番}` の形にする。
- 同一成果物・同一条件・同一評価版での判定と意味上の観測結果が安定することを確認する（反復）。
- **評価器自身は評価履歴を蓄積しない。** `--out` の下に 1 回分を書くだけであり、
  履歴として残すのは呼び出し側（校正スクリプト、外側の実行基盤）の責務である。
  確認した内容は [`inner/calibration/README.md`](../inner/calibration/README.md) §2 に記録している。
- **評価版は `1.0.0` → `1.1.0` に改訂した。** 判定の意味そのものが変わる改訂（`R-005` の観測方法の追加、
  §4.5.1）であるため、評価版を据え置かずに上げる。理由と代替案は [decision-log.md](decision-log.md) D-17 に記録している。
  過去の記録（`1.0.0` の 17 ケース）は
  [`inner/calibration/calibration-summary-1.0.0.json`](../inner/calibration/calibration-summary-1.0.0.json) に
  **履歴として残し、新しい結果で上書きしない**。最新の実行は
  [`inner/calibration/calibration-summary.json`](../inner/calibration/calibration-summary.json)（`1.1.0` の 20 ケース）。
- **重複した採点連番は、副作用の前に拒否する。** 同じ連番を再指定した場合、既存の作業領域・DB・
  標準出力ログを書き換えずに拒否し、拒否の記録は採用済みの採点記録（`index.jsonl`）とは別に保存する。
  再採点は新しい連番で行う。詳細は [`outer-harness.md`](outer-harness.md) §6.6。

## 7. 評価器の妥当性の根拠と限界

### 7.1 妥当性の根拠

| 検証 | 内容 | 記録 |
| --- | --- | --- |
| 正例 | 対象要件を満たすことを確認した成果物を通す | [`inner/calibration/`](../inner/calibration/) |
| 実行可能な負例 | 境界判定の誤り、内容の取り違え、欠落・二重処理を不合格にする（ビルド不能を落とすだけで済ませない） | 同上 |
| 妥当な別実装 | 許容した構造・表現の違いで不当に失敗させない | 同上 |
| 反復 | 同じ成果物・条件・評価版で判定が安定する | 同上 |
| 評価側障害 | 起動・データ準備・検査の障害を、実装品質の失敗と取り違えない | 同上 |

### 7.2 限界（隠さず記録する）

1. **正例を評価器と同じ作業者が書いている。** 正例が通ったことは評価器の妥当性の根拠にならない。これを補うため、(a) 要件と期待値を旧実装のコードと HTTP 契約から独立に導出して根拠を要件ごとに記録し、(b) 構造・表現の異なる「妥当な別実装」で不当に落ちないことを確認し、(c) 重要な負例を実際に落とすことを確認する。**正例の実装を「正解の定義」として扱わない。**
2. **旧実装を実行していない。** `legacy` を根拠とする期待値はコード読解に基づく。旧実装の実行時の挙動（例外時のステータスコード等）は確認していない。
3. **静的な検査の限界。** `R-029`（旧実装の非呼び出し）は成果物ツリーの走査によるヒューリスティックであり、間接的なラッパー化を証明しない。旧実装の成果物・旧ホスト・旧フレームワークの信号で判定し、**名前空間やアセンブリ名の語だけでは判定しない**（§4.6）。コメント・文字列・説明文に旧名称が現れるだけの場合も、**不合格の根拠にしない**（診断情報として記録する）。実際に不合格にするのは、`csproj` の参照・対象フレームワーク、旧ホストの起動記述、旧実行ファイル名のファイルの存在、`Global.asax`・`packages.config` のような旧構成ファイルである。この区別は字句解析に基づく近似であり、**動的な起動経路（リフレクション、外部コマンドの文字列組み立て）は依然として検出しない**。`R-026` `R-027` は起動対象プロジェクトの `csproj` に限る。
4. **観測範囲の限界。** 注文合計（`Order.Total`）は旧実装の HTTP 契約から観測できないため評価対象外とし、かご合計で代替している（§2.1）。注文明細の行構成そのものも観測していない。`R-005` は保存契約（§4.5.1）の `Orders` 表の行が再起動をまたいで残ることを確認するが、**注文の金額・住所・明細の内容が保持されていることは確認していない**。保存契約を満たさない成果物（別の表名・列名を使う実装）では保持を確認できないため、`R-005` を不合格にする。**`R-005` の合格を「注文が失われない」ことの完全な証明として使わない。**
5. **校正は部分検証である。** 用意した fixture は課題の全誤りを網羅しない。校正の通過を「すべての入力に対する完全な等価性」や「モダナイズ品質全般の保証」と表現しない。
6. **採点対象外の品質は測っていない。** §2.1 の項目について、成果物が良いとも悪いとも主張しない。
7. **公開した移行契約は、採点基準そのものではない。** 実装役に渡す契約（`outer/conditions/MS1-001/condition.json` の `migration_request`）は §4・§3 の要件を**観測できる形で書き直したもの**であり、要件の追加・削除・変更は行っていない。**契約を公開する前に受けた採点記録を「公開された契約に基づく採点」として読み替えない。**
8. **保存契約は本改訂で追加した。** §4.5.1 の保存契約（`Orders` 表・`OrderId` 列）は、`R-005` の見逃しを解消するために本改訂で公開した。追加の必要性・代替案・影響は [decision-log.md](decision-log.md) に記録している。**この契約を公開する前に受けた採点記録を、保存契約に基づく採点として読み替えない。**

## 8. 見直し条件

次のいずれかに該当する場合は、本仕様を採用せず [#3](https://github.com/fukuda-yuki/sample2/issues/3) へ課題見直しを返す。

- 期待結果を確認できない要件が残る
- 初期状態または観測が安定しない
- 重要な誤りを検出できない（校正の負例が通ってしまう）
- 評価を成立させるための簡略化で、研究に必要な依存関係（複数情報源の横断）が消える

**採点を甘くして進めない。**

## 9. 完了条件に対する状態

### 9.1 完了条件を満たしたと言えない範囲

- 正例を評価器と同じ作業者が書いている。正例が通ったことは評価器の妥当性の根拠にならない（§7.2-1）。
- 旧実装を実行していない。`legacy` を根拠とする期待値はコード読解に基づく（§7.2-2）。
- 負例は 10 種、独立した別実装は 1 つであり、課題の全誤りを網羅しない（§7.2-5、`inner/calibration/README.md` §5）。
- **注文の保持は `Orders` 表の行の存在までしか確認していない**（§7.2-4）。金額・住所・明細の内容が
  保持されていること、複数注文の順序は確認していない。保存契約（§4.5.1）を満たさない成果物では
  保持を確認できず、`R-005` は不合格になる（保存契約違反として記録する）。
- **旧実装の参照・起動の検出は字句解析に基づく近似である**（§7.2-3）。動的な起動経路
  （リフレクション、外部コマンドの文字列組み立て）は依然として検出しない。
- **重複した採点連番の拒否は、校正のケースではない**（`inner/calibration/README.md` §5-21）。
  外側の実行基盤の挙動であり、`outer/tests` と `outer/verify/verify.py` の `V-4` で確認している。
  校正が 20 件一致したことを、この確認の完了として数えない。
- 校正の通過を「すべての入力に対する完全な等価性」や「モダナイズ品質全般の保証」と表現しない。
