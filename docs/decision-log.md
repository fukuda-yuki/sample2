| 2026-09-16 | D-15 | **評価版（`evaluation_version`）は判定の意味の版**であり、**採点したビルドの同一性は別に記録する**。外側は採点のたびに呼び出した評価器の `sha256` を実測し、`record.json` `index.jsonl` 集計表に残す。条件の `evaluation.evaluator_sha256` に入れておけば一致しないビルドでの採点を拒否し、`null`（＝固定しない）でも実測値は毎回記録する。**実モデル比較の前にこの値を確定する。** 評価器のビルドを変えて意味が変わらない場合は評価版を据え置いてよいが、校正の再実行で意味が変わらないことを示して記録する。**この値はソースの版ではなく、ビルドした場所と SDK に依存する**（同じソースでも別のパスでビルドすると変わる）。別マシン・別パスでの一致は期待せず、意味の同一性の根拠に使わない。固定するときは条件の `evaluation.evaluator_build` にソースの位置・アセンブリ・ビルドコマンド・**ビルドに使った SDK の版**・固定値の出所を書く（`source_path` `command` `sdk_version` `sha256_origin` が必須）。欠けたまま固定すると採点せずに条件の誤りとして拒否し、固定値と一致しないビルドでの採点は例外で捨てずに `rejected_mismatch` の記録として残す（固定値と実測値の両方が `mismatches` に入る）。**ビルドしたコミットは値に混ぜない。** .NET SDK は既定で作業ツリーのコミットを `AssemblyInformationalVersion` に埋め込むため、この値を測ってから記録をコミットすると次のビルドの値が変わり、**記録した値とその記録を含むコミットが一致しえない**（実測: `45a2b4a` のビルドは `76ae7269…`、`6675e19` のビルドは `60c8fbd4…`、アセンブリに `6675e19` を確認）。評価器はこの属性を読まないので `MusicStore.Evaluator.csproj` で埋め込みを切り、値がソース・パス・SDK で決まるようにした（判定の意味は変わらないため評価版は据え置き）。ビルドしたコミットは `evaluation.evaluator_build.source_commit` に追跡用として残す。**この値はソースファイルのバイト列（改行コードを含む）にも依存する**（同じ `.cs` を CRLF でビルドすると値が変わる。実測: LF `d6798301…`、CRLF `d5443910…`。`.csproj` のバイト列は効かない）。基準は `.gitattributes` の `eol=lf` のままチェックアウトした作業ツリーであり、**記録に使う値は追跡ファイルを書き換えていないクリーンな作業ツリーで測る**。**測って記録するだけでは足りない**: 外側の検証が `bin` `obj` を消した作り直しを `V-0b` で確かめ、さらに**記録コミットの後で作り直して同じ値になることを確かめてから**固定する（手順は `inner/calibration/README.md` §4.3）。この手順を踏まずに固定すると、条件に再現しない値が入って採点がすべて拒否される（拒否は記録に残るので静かには壊れない）。固定する前に測った古い値（`76ae7269…`、`09679d52…`）はこの条件を満たしておらず、再現値として扱わない。 | PMO レビュー #5 の指摘。`docs/evaluator.md` の「成果物のハッシュが同じで、評価版と条件が同じなら判定は安定する」が、評価版を据え置いたまま評価器を差し替えると成立しない。`evaluatorSha256` は `evaluationId` に入らず、`check_mismatches` もビルドを見ず、`record.json` にも無かったため、記録から採点したビルドを引けなかった。[evaluator.md](evaluator.md) §6.2、[outer-harness.md](outer-harness.md) §6.4 |
