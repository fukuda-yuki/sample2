# MS1 catalog confirmation: fixed design, no acquisition

**Recommendation: 320 Runs per condition, 320 adjacent pairs, at most 640
model Runs, and no replacements.** This is one fixed design for review and
later authorization. It estimates quality and tests token reduction; it is
**not an adequately powered claim of quality equivalence**. No new model
execution is authorized by this document.

The technical connection pilot is accepted and closed. The accepted PR #13
head is `3c2f61926e8427eca3efcbdb4784f5373b5f9cf9`; the implementation baseline
is merge `b5083f0a296a8afb4d9161825f5bf9ceedab457e`. Their trees match. This
work adds planning and offline analysis only. The original four-Run plan,
observations, evaluation recovery, and historical artifacts remain preserved.

The [machine-readable plan](../research/protocols/ms1-catalog-confirmatory-v1.json)
contains every allocated slot and its order, fixed identities, decision rules,
and stops. [Design calculations](../research/design-results/catalog-confirmatory-v1.json)
are generated by [catalog_design.py](../research/catalog_design.py).
[catalog_confirmatory.py](../research/catalog_confirmatory.py) implements the
analysis; [tests](../research/tests/test_catalog_confirmatory.py) exercise its
meaning and edge cases. The [validation record](ms1-catalog-confirmatory-validation.md)
records what was actually checked. The separate [misc amendment proposal](ms1-catalog-confirmatory-misc-proposal.md)
has not been applied to the research canonical repository.

## 1. Question, scope and population

With identical original source, derived catalog, and retrieval capabilities,
what effect does omitting the large initial source excerpt have on public
requirement compliance and total provider-reported tokens over an entire Run?

Keep [catalog-expanded / catalog-compact](ms1-catalog-return-two-condition-spec.md)
unchanged. The appended initial packet is the sole intervention. Later source
or derived-data retrieval is allowed in both conditions. Do not add deletion
hints, instructions not to read, another task, model, or condition. Increased
retrieval, retention, calls, or implementation/verification work is an outcome,
not noncompliance with the intervention.

Only new, allocated Runs after the design freeze enter the confirmatory
population. The four technical pilot Runs and all historical/exploratory Runs,
including supplements, are excluded. The pilot informs scale and operational
risks; its 1/2 versus 2/2 pass counts and 15.9% token difference are **not**
population parameters, power assumptions, or additional confirmatory samples.

The experimental unit is a **Run**. Each pair has two fresh workspaces,
sessions, state directories, and one Run per condition. A pair is an adjacent
time block, not the same generated product, seed, or model trajectory. Calls
within a Run are dependent observations, never extra experimental units.

Use the same task, source commit, model, OpenCode, worker/gateway/evaluator
images, browser dependencies, compaction, and deadlines as the accepted
implementation, with the existing post-pilot environment forwarding fix.
The JSON pins their identities. There is no new evaluator or runtime build.

## 2. Allocation, timing and estimands

The saved schedule uses one independent fair order draw per pair with
`random.Random(2026092001).getrandbits(1)`: 0 means compact first. There are
173 compact-first and 147 expanded-first pairs. This realized imbalance is
retained, not repaired by choosing another seed. Each pair still has both
conditions. The exact 640-slot sequence is saved before any new dispatch.
Attempts 1001–1320 in a new cohort directory prevent confusion with pilot IDs.

Run serially, finishing a pair before starting the next. Start a pair only
when there is capacity for both members; planned session breaks occur between
pairs. Record UTC start/end, within-pair delay, pauses, model IDs, cache/usage
shapes and environment identities. An interrupted pair stays at its original
position on resumption. Do not regroup by condition or re-pair by outcome.
Randomized order reduces systematic period bias; it cannot guarantee absence
of provider drift, carryover, or correlation across days.

| Endpoint | Fixed estimand / role |
|---|---|
| Tokens, primary | Mean of `T_compact - T_expanded` across all allocated pairs; T sums provider input + output over every call in the Run |
| Tokens, companion | Ratio of arithmetic Run means, compact / expanded; not the mean of Run ratios or a geometric ratio |
| Quality, primary | Difference in probability of passing **all 29** public requirements, compact minus expanded |
| Quality detail | Per-requirement pass, fail and unknown/blocked counts, always with assigned denominator; confirmed failures and incomplete coverage separately |
| Descriptive | Input/output totals separately; call count; mean/max input per call within Run; source/derived-data retrieval; bytes returned and later retained; implementation/verification activity |
| Secondary only | Success-only token summaries and complete-pair summaries when primary data are missing |

Cache-read and reasoning subtotals are already included in provider input and
output; do not add them again. Missing usage is null, not zero. Source bytes,
retained bytes, wall time, provider tokens and currency are distinct measures.

## 3. Prespecified inference and decision rules

### Tokens

For complete pairs, let `d_i = T_Ci - T_Ei`. Report the arithmetic mean and
the two-sided 95% interval

`mean(d) +/- t_(0.975, n-1) * sd(d) / sqrt(n)`.

Support token reduction only when its upper endpoint is strictly below zero
(one-sided alpha 0.025). This is a paired mean analysis, not a rank or median
test. It agrees with [SciPy's paired t procedure](https://docs.scipy.org/doc/scipy/reference/generated/scipy.stats.ttest_rel.html).
Keep failed products, timeouts, early stops and technical attempts with fully
observed usage. No trimming, winsorization, log transformation, selection of
the favorable endpoint, or exclusion for usage-format changes is permitted.

Report a fixed 20,000-resample **pair** percentile bootstrap for the mean
difference and ratio of arithmetic means (seed 2026092101), as a sensitivity
analysis. Report order-stratum mean differences and influence of large Runs
descriptively. These never replace the primary result. If sensitivities
disagree, present that fragility alongside the primary interval. Identical
observed differences return a point estimate but no zero-width population
interval and cannot support a confirmatory decision.

The t interval is exact for normal independent pair differences and otherwise
an approximation. Simulations below examine finite-variance skew and long
tails. Arbitrary heavy tails, shared provider regime changes and dependence
between pairs are not covered by those simulations. These assumptions limit
the claim to this fixed task/runtime and its sampled operating regime. Do not
switch methods after observing unfavorable skew or precision.

### Quality: a strict relative rule, without an invented tolerated loss

The reviewed `sample2` specification and the three canonical `misc` documents
contain **no justified positive loss margin** and no population pass-rate
floor for practical deployment. The existing 29-requirement Run contract is
unchanged. Failure to find a difference does not establish maintenance;
equivalence/noninferiority needs a defensible bound. See
[Lakens on equivalence](https://lakens.github.io/statistical_inferences/09-equivalencetest.html).

Use the conservative rule `lower95(p_C - p_E) > 0`. This demands evidence of
**relative quality superiority**; it is not an ordinary positive-margin
noninferiority test and must not be called equivalence. If true quality is
equal, no finite sample size can make this rule accept with 80% probability.
More Runs do not solve the missing margin justification.

Let `w` count pairs where compact passes and expanded fails, and `l` the
reverse. The point estimate is `(w-l)/n`. Construct two equal-tail **97.5%**
Clopper–Pearson intervals, one each for `w/n` and `l/n`, then use
`[L_w - U_l, U_w - L_l]`. Each cell count is binomial marginally under
independent identically distributed pairs. A union bound gives at least 95%
simultaneous coverage, without assuming independence between the cell counts.
This conservative construction is intentionally wider than some specialized
paired-score intervals. The beta-quantile implementation is cross-checked
against [SciPy's exact binomial interval](https://docs.scipy.org/doc/scipy/reference/generated/scipy.stats.binomtest.html).

If all 320 pairs pass in both conditions, the difference is 0 and its interval
is **[-1.36005, +1.36005] percentage points**, not [0,0]; relative maintenance
remains unconfirmed under the zero-loss rule. All-fail pairs give the same
relative interval and plainly provide no adequate products. Report each
condition's pass count/rate and exact 95% interval as well.

No category below establishes practical sufficiency, visual fidelity, human
acceptance, or general modernization quality. There is no authorized absolute
population quality floor. Even a relative superiority result at low pass
rates must retain that limitation. Do not label an individual failed product's
lower tokens an efficiency improvement.

### Decision table (in this precedence order)

| Code | Rule and allowed conclusion |
|---|---|
| `indeterminate` | Missing total usage, unknown quality, incomplete coverage, unresolved identity/cleanup faults, or undefined token interval: preserve estimates available, but no joint decision |
| `token_reduction_not_supported` | Complete valid data, token interval upper bound >= 0: token reduction unsupported; this is not proof of no effect |
| `token_reduction_and_relative_quality_supported` | Token upper bound < 0 AND quality lower bound > 0: both prespecified **relative** conditions supported, practical adequacy still unestablished |
| `token_reduction_quality_not_supported_or_unresolved` | Token upper bound < 0, quality lower bound <= 0: tokens reduced; quality condition not supported. Upper quality bound < 0 indicates degradation, otherwise the quality claim is unresolved |

The joint claim is a conjunction of the two directional criteria, so it does
not select whichever endpoint succeeds. No multiplicity adjustment is needed
for that intersection claim. Other endpoints, 29 requirement comparisons,
orders, usage shapes and behavioral associations are descriptive, without
additional confirmatory hypothesis claims. No joint power is inferred by
multiplying token and quality powers: their dependence is unknown.

## 4. Sample size: why 320 per condition, and what it cannot resolve

Power and precision are different design goals. A sample-size justification
must identify which one drives each endpoint rather than rely on an unstable
pilot effect. See [Lakens on sample-size justification](https://lakens.github.io/statistical_inferences/08-samplesizejustification.html).

Prespecify a token planning alternative of **600,000 fewer tokens per Run**,
20% of a rounded expanded reference scale of 3,000,000. This is an explicit
design judgment about a substantial reduction in accumulated context, not an
empirically proven utility threshold, pilot estimate, or monetary saving.
Also calculate 10% and 30% alternatives. A study powered to detect a true 20%
reduction against zero is **not** powered to prove a reduction of at least 20%.
The latter requires the upper interval below -600,000 and is reported separately.

The reference token scenario has coefficient of variation (SD/mean) 1.0 and
within-pair token correlation 0.25. The normal paired-difference approximation
requires 246 pairs for 80% power at a true 20% reduction; at 10% it requires
1,070 pairs. These are assumed population moments, not estimates from two
Runs per condition. The simulation uses paired lognormal draws with latent
correlation calibrated to the requested token correlation.

The quality design target is **about +/-10 percentage points of interval
precision**, at assumed p_C = p_E = 0.8 and binary pair correlation 0. This is
an estimation target, **not a tolerated quality loss**. It does not change the
strict zero-loss decision. The recommended size is the smallest prespecified
candidate meeting this precision goal and at least 80% reference token power.

Each simulated cell has 20,000 replicates, seed 2026092002. Monte Carlo standard
errors and Wilson intervals are in the JSON; their uncertainty excludes model
misspecification. No pilot resampling supplies these distributions.

| Runs per arm / pairs | Total Runs | Token power, true 20% reduction, reference lognormal | Quality interval mean half-width, p=0.8/rho=0 | 90th percentile half-width |
|---:|---:|---:|---:|---:|
| 40 | 80 | 21.1% | 27.18 pp | 29.89 pp |
| 80 | 160 | 38.5% | 19.17 pp | 20.65 pp |
| 160 | 320 | 64.8% | 13.46 pp | 14.23 pp |
| **320** | **640** | **90.7%** | **9.44 pp** | **9.82 pp** |
| 640 | 1,280 | 99.5% | 6.63 pp | 6.82 pp |

At 320 pairs, a true 10% reduction has only 34.2% power in the reference
lognormal scenario. A longer-tailed CV=1.5, correlation=0 scenario gives 49.3%
power for 20% reduction. Independent 2% tenfold contamination gives 53.9%
(actual CV about 1.53, correlation about 0.060). Negative token correlation
-0.25 at CV=1 gives 71.3%. The fixed size does not guarantee detection if the
assumptions are wrong. Retain the wide interval and limited conclusion.

Quality precision also varies: at 320 pairs the mean half-width is 11.09 pp
for p=0.5/rho=0, 7.08 pp for p=0.8/rho=0.5, and 10.12 pp for p=0.8/rho=-0.2.
At the maximum discordance configuration, the interval half-width at expected
counts is about 12.78 pp. This is not uniformly a +/-10 pp design.

The quality rule is often the limiting endpoint. Exact multinomial summation
of the **same implemented rule**, separate from Monte Carlo, gives:

| Assumed p_C / p_E / binary rho | Quality support probability at 320 | First evaluated size with >=80% support (not a mathematical minimum) |
|---|---:|---:|
| 0.85 / 0.80 / 0 | 8.48% | 2,560 pairs (95.97%; 1,280 pairs give 63.67%) |
| 0.95 / 0.90 / 0.5 | 54.56% | 640 pairs (95.26%) |
| 1.00 / 0.95 / 0 | 92.78% | 320 pairs |
| Equal rates | At most the rule's type-I error, often much smaller | **No finite size gives 80% support for zero-margin superiority** |

Thus 320 is recommended for a bounded, informative comparison with a strict
possibility of joint support, **not sufficient validation of quality
maintenance at equal rates**. Modest quality gains may remain unresolved too.
If the essential requirement is a high-probability conclusion of maintenance
under equal quality, do not launch this as a promise to deliver that conclusion:
a justified quality tolerance would require a separate, pre-data scientific
decision. This plan does not invent one or broaden it to lower the Run count.

## 5. Resource requirement, not a purchase or availability claim

| Pairs | Provider tokens at 2M / 3.2M / 6M per Run | Sum of 1,800-second Run budgets |
|---:|---:|---:|
| 40 | 0.16 / 0.256 / 0.48 billion | 40 h |
| 80 | 0.32 / 0.512 / 0.96 billion | 80 h |
| 160 | 0.64 / 1.024 / 1.92 billion | 160 h |
| **320** | **1.28 / 2.048 / 3.84 billion** | **320 h** |
| 640 | 2.56 / 4.096 / 7.68 billion | 640 h |

Scaling the four reported pilot Runs gives **2,035,824,640 provider tokens**
and **132.49 hours** of their runtime interval for 640 Runs. This is only an
arithmetic scale reference, with no distribution or capacity guarantee.
Runtime excludes subsequent cleanup, evaluation, archival, and operator pauses.
At assumed additional 60–300 seconds per Run, those operations add 10.67–53.33
hours. At assumed retained storage of 0.1–1 GiB per Run, reserve 64–640 GiB;
these are scenarios, not measured storage demands. Recovery can add time.

For comparison, 2,560 pairs would scale to 16.29 billion provider tokens and
2,560 hours of Run budgets, before evaluation/archival. Neither quota, available
machine time nor a monetary budget has been supplied. Therefore feasibility
at either size is **unverified**. Time deadlines do not impose a deterministic
total-token ceiling. Do not imply these tokens equal billed tokens, money, or
newly available quota. If capacity cannot support the fixed cohort, defer
acquisition; do not shrink the count and call it sufficient confirmation.

## 6. Stops, recovery and missingness

- **Product failure:** preserve, score as observed, and continue. No stopping,
  replacement, extra attempt or helpful hint because a product failed.
- **Evaluation/browser fault:** stop before next dispatch; recover by ordinary
  `rescore` of the same frozen artifact. Preserve the first and every later
  evaluation. At most two recovery rescores per artifact, within 72 hours of
  the technical halt. These are not model Runs. If still unresolved, terminate
  acquisition and report the incomplete allocated cohort.
- **Authentication/quota, model, input, original-source/fixed-byte mismatch,
  uncertain dispatch, or unconfirmed owned cleanup:** stop new dispatch.
  Diagnose without generation; preserve the fault and all observations.
  No model fallback, purchase, credential switch or unowned cleanup.
- **Resumption:** within the same 72-hour window, require recorded cause and
  repair, fresh equality of all frozen identities and browser dependencies,
  complete saved-evidence reconciliation, and owned cleanup confirmation.
  Continue only slots proven never dispatched, in their original sequence.
  An attempted or uncertain slot is never replayed. If a fixed condition must
  change, close this cohort as incomplete instead of silently amending it.
- **Usage shape change:** retain all calls/Run, describe shape, transmission
  and retention separately. If primary input/output remain complete it is not
  a stop. If primary usage cannot be reconciled, halt for evidence recovery;
  do not remove the Run or attribute call growth to shape alone.
- **Interim results:** no outcome-based early success, futility stop, extension,
  sample-size re-estimation or replacement. Operational checks may inspect
  failures; condition comparisons wait until the fixed cohort closes.

A verified, attempted pre-dispatch technical failure can have measured zero
usage only with affirmative evidence of no provider dispatch. An unstarted,
uncertain or partially observed slot is null. All allocated slots remain in
the denominator. A complete token total includes fully observed usage from
failed/timed-out attempts; it need not require successful completion.

For quality, a verified failure of any requirement fixes all-29 success at 0,
even when other requirements lack coverage. Report both facts. With no known
failure and incomplete evaluation, success is unknown, not 0 or 1. Report
pass/assigned, pass/artifact, known-fail and unknown counts. For unknown
outcomes, give best/worst sample-rate bounds and a conservative confidence
envelope: fill unknown compact=0/expanded=1 for the lower bound, reverse for
the upper bound, and use the same paired interval. Even a robust envelope
cannot bypass this plan's complete-coverage requirement for joint support.

If any total usage is unknown, there is no all-assigned token point estimate
or primary interval. Known partial sums and complete-pair contrasts are
secondary, explicitly selected observations. No missing-at-random assumption,
zero imputation or success-only analysis rescues a primary conclusion.

## 7. Execution and analysis handoff

There is no new acquisition launcher. Reuse the ordinary harness per saved
slot in a later authorized execution task; the four-slot `catalog_pilot
execute` command deliberately refuses this plan. The future operator must:

1. Save the immutable plan hash, these analysis code hashes, accepted source
   revision, runtime/image/source/profile identities, and explicit resource
   availability in a pre-dispatch launch receipt. Reuse accepted connection
   evidence, validate current pins and existing browser dependencies, and
   forward `NODE_PATH` and `SAMPLE2_BROWSER_EXECUTABLE` with the existing
   `child_environment` helper. No repeat pilot is required.
2. Create the new cohort directory exclusively. Save a durable dispatch
   intent with the exact slot before each ordinary CLI call; record its
   exit/result and archive receipt after. Existing or uncertain intents
   cannot be replayed. Use `outer.harness.cli --runs-dir <cohort> run --task
   MS1-001 --intervention <slot.condition> --runtime deepseek-catalog-v1
   --attempt <slot.attempt>` with the existing safe child environment.
3. Apply the stops above after each Run; preserve all raw requests/responses,
   native logs, fixed artifacts, evaluation sequence, and cleanup manifests.
   Finish all 640 allocated slots, or close with incomplete/stop reasons.
4. Run the existing read-only `research.catalog_observations` with this plan.
   Its inherited `interpretation` text says technical pilot; cohort ID and
   plan hash control the new analysis, not that text. No reader/evaluator
   redevelopment is required. The observer's `case`, `calls`, `tokens`,
   `requirements`, `row`, `initial_input`, and cleanup fields are the input
   schema. A missing slot is kept; extras/duplicates/identity contradictions
   are rejected. Invalid model/input/evaluator evidence retains the attempted
   Run but prevents a confirmatory decision.
5. Run the fixed analysis once after closure. Include the pre-dispatch receipt
   bound to this plan. Preserve any subsequent correction as another output,
   never overwrite the original. Report decision, both intervals, assumptions,
   missingness, and all assigned denominators before behavioral interpretation.
