# 評価器の校正（`inner/calibration`）

[品質評価仕様 §7.1](../../docs/quality-spec.md) が求める 4 分類の校正を実行し、その結果を記録する。

- 実行: [`run-calibration.ps1`](run-calibration.ps1)
- 生の記録: [`calibration-summary.json`](calibration-summary.json)（実行時に生成される実際の出力）
- 評価器の契約: [docs/evaluator.md](../../docs/evaluator.md)
- **モデルは一切呼び出さない。** 成果物を固定し、評価器だけを検証する。

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\inner\calibration\run-calibration.ps1
```

## 1. 校正の方法

成果物のハッシュが同じでも評価は決定的なので、**期待を実行前に宣言する**。
各ケースについて次を固定し、実結果と完全一致で突き合わせる。

| 宣言する項目 | 内容 |
| --- | --- |
| 期待する判定 | `pass` / `fail` / `fail_critical` / `blocked` / `error` |
| 不合格になる要件の集合 | 要件 ID の集合（完全一致） |
| 未評価になる要件の集合 | 要件 ID の集合（完全一致） |
| 終了コード | `0` / `1` / `2` |
| 品質点の有無 | `null` か否か |

「落ちてはいけない要件」を指定するだけでは足りない。**集合の完全一致**にすることで、
予期しない不合格（誤検出）と予期しない合格（見逃し）の両方を検出する。

`runs/` は `.gitignore` の対象であり、実行のたびに作り直される。
追跡する記録は本ファイルと `calibration-summary.json` だけである。

## 2.1 成果物ハッシュの扱い

成果物ハッシュは**成果物ディレクトリ配下の全ファイル**を対象にする（`bin` `obj` `.git` を除く）。
したがって、成果物ディレクトリの中に研究用の文書やメモを置くと、その編集でハッシュが変わってしまう。
実際、正例の説明文書を `inner/fixtures/reference/` の中に置いていたため、その文書の編集で
同じ成果物のハッシュが変わった。現在は説明文書を [`inner/fixtures/README.md`](../fixtures/README.md) に移し、
`reference/` `alternative/` の直下には成果物そのものだけを置いている。

## 3. 4 分類の対応

| 仕様 §7.1 の分類 | ケース | 何を確認するか |
| --- | --- | --- |
| 正例 | `cal-ref-001` `cal-ref-002` | 対象要件を満たす成果物を落とさない。反復で判定が変わらない |
| 実行可能な負例 | `neg-*` の 7 種 | 内容の取り違え・欠落・二重処理を実際に不合格にする |
| 妥当な別実装 | `cal-alt-001` `cal-alt-002` | 構造・表現の違いで不当に落とさない |
| 評価側の障害 | `fault-*` の 2 種 | 起動・データ準備・検査の障害を実装品質の失敗と取り違えない |

### 3.1 負例が何を壊すか

| 負例 | 壊す内容 | 期待どおり落ちた要件 |
| --- | --- | --- |
| `remove-count-pre-decrement` | 削除応答の数量を減算前に読む | `R-014` |
| `no-quantity-multiply` | かご合計で数量を掛けない | `R-013` `R-016` |
| `duplicate-cart-lines` | 同じアルバムでも明細を増やす | `R-012` `R-013` `R-014` `R-015` `R-016` |
| `no-seed` | 初期カタログを投入しない | `R-002` `R-003` `R-004` `R-005` `R-006` `R-008` `R-010` `R-011` `R-012` `R-013` `R-014` `R-016` `R-017`（+ 未評価 `R-023` `R-024`） |
| `destructive-seed` | 起動のたびに DB を作り直す | `R-005` |
| `unknown-album-500` | 存在しないアルバムを 404 にしない | `R-009` |
| `legacy-wrapper` | 旧実装を起動する記述を残す | `R-029` |

負例は [`inner/fixtures/negatives/apply.ps1`](../fixtures/negatives/apply.ps1) が正例のコピーに
1 箇所ずつ改変を加えて作る。改変のアンカーが一意に存在することを適用時に検査する。

`no-seed` は**検出したい欠陥が連鎖して落ちる**例である。カタログが無いと、
カタログを前提とする要件がまとめて落ちる。一方、404 系（`R-007` `R-009`）と
注文系（`R-018`〜`R-025`）は落ちない。この「落ちないこと」も集合の完全一致で固定している。

## 4. 校正で見つけて直した誤り

校正は評価器と fixture の欠陥を実際に検出した。**検出した内容を隠さず残す。**

| # | 事象 | 原因 | 対応 |
| --- | --- | --- | --- |
| 1 | `neg-remove-count-pre-decrement` が**通ってしまった**（見逃し） | `apply.ps1` の改変アンカーが 1 行だけで、`if (item.Count > 1)` の内側に一致していた。挿入した代入が直後の行で上書きされ、改変が無効になっていた | アンカーを 2 行にし、対象の代入順序を実際に入れ替えるようにした |
| 2 | `neg-no-seed` が `R-023` `R-024` を**誤って不合格にした**（誤検出） | カタログが無いと かごに明細を入れられない。入力検証の検査は前提不成立なのに `fail` を返していた | 前提不成立を `blocked` として返すようにした（`C-024` `C-025`）。期待も `blocked` として宣言 |
| 3 | `fault-unimplemented-check` が `evaluation.json` を**書かなかった** | 明示した `--spec` のディレクトリに `catalog.json` が無く、台帳の読み込み前に終了していた | 台帳・カタログの読み込み失敗と成果物ディレクトリの不在を評価側の障害として集約し、必ず `evaluation.json` を書くようにした。あわせて `--catalog` を明示 |
| 4 | 校正スクリプトが負例の生成失敗を**見逃しえた** | 子スクリプトの `$LASTEXITCODE` に依存していた | 生成後に成果物ディレクトリの存在を確認するようにした |
| 5 | 同じ成果物の**ハッシュが変わった** | 成果物ディレクトリの中に研究用の説明文書を置いていたため、その文書の編集がハッシュに影響していた | 説明文書を [`inner/fixtures/README.md`](../fixtures/README.md) に移した（§2.1） |

事象 1・2 は「期待を実行前に宣言して完全一致で突き合わせる」方式にした理由そのものである。
`pass` になるはずのないケースが `pass` になっても、宣言した集合と一致しなければ校正は失敗する。

## 5. 校正の限界（隠さず記録する）

1. **正例を評価器と同じ作業者が書いている。** `cal-ref-*` が通ったことは評価器の妥当性の根拠にならない。
   正例の実装を「正解の定義」として扱わない。根拠は要件ごとの `basis` と、別実装・負例の校正に置く。
2. **負例は 7 種であり、課題の全誤りを網羅しない。** 校正の通過を
   「すべての入力に対する完全な等価性」や「モダナイズ品質全般の保証」と表現しない。
3. **負例は正例の 1 箇所改変である。** 複数の欠陥が同時に存在する場合の判定は確認していない。
4. **旧実装を実行していない。** `legacy` を根拠とする期待値はコード読解に基づく。
   負例が「旧実装と同じ挙動」であることの確認ではない。
5. **別実装は 1 つだけである。** 構造・表現の違いのうち、この 1 つが示す範囲でしか
   「不当に落とさない」ことを確認していない。別実装は 最小 API・素の SQLite・文字列組み立て HTML を使い、
   正例（MVC・EF Core・Razor ビュー）とは実装方式を変えている。
6. **評価側の障害は 2 種だけである。** 発行の失敗、起動のタイムアウト、ポート衝突などは
   宣言した期待として固定していない。
7. **環境依存。** 校正は `dotnet` の版とポートの空き状況に依存する。実行環境の `dotnet --version` は
   本ファイルに記録しているが、`evaluation.json` には記録していない。別環境での再現は確認していない。
8. **測っていない品質がある。** 仕様 §2.1 の項目について、成果物が良いとも悪いとも主張しない。
9. **成果物ハッシュは成果物ディレクトリの置き方に依存する。** 同じ実装でも、成果物の外に置く文書を
   中に移せばハッシュは変わる。ハッシュは「この木を評価した」ことの識別子であり、
   「実装の意味が同じ」ことの証明ではない（§2.1）。
