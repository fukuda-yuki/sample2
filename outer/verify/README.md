# 外側：非モデル検証の記録

対応 Issue: [#5](https://github.com/fukuda-yuki/sample2/issues/5)。仕様は [docs/outer-harness.md](../../docs/outer-harness.md)。

`verify.py` は、[docs/outer-harness.md](../../docs/outer-harness.md) §10.1 の各項を
**実評価器と実装で実際に突き合わせる**ドライバである。期待は実行前にコード上で宣言し、
観測値と**完全一致**で突き合わせる。一致しなければ `verification-summary.json` の
`mismatched` に残り、終了コードは `1` になる。

- 生データ: [`verification-summary.json`](verification-summary.json)
- 本ファイル: その読み方と、**測っていないこと**の記録

## 何を主張し、何を主張しないか

**主張すること。** モデルを一切呼ばずに、Run の作成 → 実行 → 停止確認 → 成果物の回収と固定 →
実評価器による採点 → 再採点 → 保存済み資材だけからの再集計 → パッケージの検証と復元
までが、実装と実評価器の組み合わせで通ること。評価器が返した `verdict` `quality` を
外側が書き換えず、評価側の障害を実行の失敗として記録しないこと。
採点に使った評価器のビルドを外側が実測して記録していること。

**主張しないこと。** 実モデル実行の結果。エージェントの出力の品質。
研究の条件間の比較。別環境での再現。§10.1 の全項目（下の「限界」を参照）。

## 実行方法

```powershell
cd <repo root>
python outer\verify\verify.py --repo .
```

- 作業ディレクトリ: `runs/_verify`（追跡しない）と `outer/verify/.scratch`（追跡しない）。
  実行のたびに**消してから作り直す**。
- 所要時間: 約 40 秒（`dotnet build` は増分ビルド。初回はこれより伸びる）。
- 終了コード: 全ケース一致で `0`、不一致ありで `1`、評価器をビルドできなければ `1`。

### V-4 重複の拒否

同じ成果物・同じ評価版・同じ連番で 2 回目の採点を試みる。

| 観測項目 | 値 |
| --- | --- |
| 送出された例外 | `FileExistsError` |
| `evaluations/` のディレクトリ数（前 → 後） | `1` → `1` |
| `evaluations/index.jsonl` が不変か | `true` |

仕様 §6.1 の「同じ `evaluation_id` を 2 つ作らない」の確認である。
**「同じ成果物を 2 回評価すると同じ評価 ID になる」ことは主張しない。**
評価 ID は連番を含むため、同じ ID が再現するのは**同じ連番のときだけ**である（§6.1）。
重複を防ぐのは外側の責務であり、評価器自身は履歴を持たない。

### V-5 再採点

連番を 1 進めて同じ成果物を採点し直す。

| 観測項目 | 値 |
| --- | --- |
| `verdict` / `quality` | `pass` / `100`（1 回目と一致） |
| 外側の `artifact_sha256` | 1 回目と一致 |
| 評価 ID の先頭 12 桁が一致 | `true` |
| 連番の差 | `1` |
| `index.jsonl` の行数 | `2`（履歴が増える） |
| 採点に使った作業ディレクトリが別か | `true`（`['001', '002']`） |
| 作業ディレクトリに DB が作られたか | `2` 件（どちらも自前の DB） |

差が**連番と作業ディレクトリだけ**であることの確認である。§10.1 の「同じ成果物を 2 回評価すると
同じ判定・同じ品質点になる」はこの形（連番を進めた再採点）で測っている。

採点のたびに `evaluation-work/<連番>/` を作り直すのは、**前回の採点が残した DB を
次の採点が引き継がない**ためである。引き継ぐと「毎回空の DB から始める」という初期条件が
崩れ、再起動をまたいだ注文の増減を測れなくなる（`R-005` の見逃しと対になる欠陥）。
`work_dirs_with_db` が `2` であることは、**2 回の採点がそれぞれ別の DB を作った**ことの確認である。

### V-14 採点が成果物ディレクトリを書き換えない

`V-2` の正例の Run について、`frozen/` のファイル一覧を
回収時のスナップショット（`snapshot.json` の `frozen`）と突き合わせる。

| 観測項目 | 値 |
| --- | --- |
| スナップショットに無いファイル（増えた） | `[]` |
| スナップショットにあるが実在しないファイル（消えた） | `[]` |
| ファイル数 | `29` |

`dotnet publish` は既定で**発行するプロジェクトの下**に `obj/` と `bin/` を書く。
成果物をそのまま発行すると、採点の前後で `frozen/` の中身が変わり、
**採点した成果物と固定した成果物が別物になる**。評価器は成果物を作業ディレクトリへ
複製し（`<work>/source`）、複製に対して発行する（`docs/evaluator.md` §3）。
この検査は、その規則が**実際に成果物を触っていない**ことの確認である。

`bin` `obj` は成果物ハッシュの除外規則（仕様 §4.2）で無視されるため、
この書き換えは `artifact_sha256` には現れない。**ハッシュの一致だけでは
成果物が書き換わっていないことを示せない**ので、ファイル一覧で測っている。

| 評価器の終了コード | `0` |

### V-11 採点した評価器ビルドの記録

正例の Run（V-2 と V-5 で 2 回採点されている）の記録を、外側が実測した値と突き合わせる。

| 観測項目 | 値 |
| --- | --- |
| `record.json` の `evaluator_sha256` が、評価器の DLL を外側で計算した `sha256` と一致 | `true` |
| `evaluator_sha256_reported`（評価器が `Assembly.Location` から出した申告）が同じ値と一致 | `true` |
| `index.jsonl` の全行（2 行）の `evaluator_sha256` が同じ値と一致 | `true` |
| 集計表の `scoring.evaluator_sha256` が同じ値と一致 | `true` |
| `evaluation_version`（`1.0.0`）がビルドのハッシュと異なる | `true` |
| 条件が固定していないとき、`evaluator_sha256_pinned` が `null` で記録される | `true` |

実測した値は `verification-summary.json` の `artifacts.evaluator_sha256` にある
（本記録では `4eeca67bd2206b78…`）。**「外側が呼び出したものを実測している」ことの確認であり、
その値が別のマシンや別のパスで再現することの確認ではない**（限界 15）。
採点に使う前に、**評価器を `bin` `obj` を消してからビルドし**（`V-0`）、
**もう一度消して作り直して同じ値になること**を `V-0b` で確かめている
（`artifacts.evaluator_sha256_rebuild` が `artifacts.evaluator_sha256` と一致する）。
`V-0` のビルドを消してから始めるのは、**残っていた `bin` `obj` が前のビルドの設定を引き継ぐ**ためである
（作り直しの値と一致しないことを実測で確認した）。**繰り返せないビルドの値を
「どのビルドで採点したか」の記録に使わない。**
「評価器が申告した値をそのまま写していない」ことは、代替評価器が別の値を申告する
`outer/tests` の `test_the_recorded_build_is_what_the_outer_invoked_not_what_was_claimed`
で確認している。

条件の `evaluation.evaluator_sha256` に固定値を入れたときの扱いは、この検証では
**代替評価器でしか**確認していない（限界 17）。

- 固定値があって `evaluation.evaluator_build` が欠けていれば、採点のディレクトリを作る前に拒否する
  （`test_pinning_without_provenance_is_refused`）。必須は
  `source_path` `command` `sdk_version` `sha256_origin` `clean_worktree` の 5 つであり、
  `clean_worktree` は `true` でなければ拒否する
  （`test_pinning_a_build_measured_outside_the_procedure_is_refused`）。
  固定値とその出所が離れないようにするため。
- 固定値と一致しないビルドでの採点は、例外で捨てずに `rejected_mismatch` の記録として残す
  （`test_a_different_evaluator_build_is_refused_when_the_condition_pins_one`）。
  固定値と実測値の両方が `mismatches` に入るので、**静かに通ることも、診断できないまま消えることもない**。
  この記録は `index.jsonl` にも載る（`test_the_refused_build_is_kept_in_the_index`）。

### V-12 検証の前後でアプリのプロセスが増えていない

検証の開始前と終了後に、この機械の `dotnet <…>MusicStore.Web.dll` のプロセス ID を集める。

| 観測項目 | 値 |
| --- | --- |
| 増えたプロセス | `[]`（増えていない） |

**「増えていない」ことの確認であり、実行中に一時的に立つことの確認ではない。**
開始前に残っていたプロセスは差し引くため、この検査は
**検証開始時点で残骸が無いこと**を前提にしている。
`V-10` は「残ったときに特定できるか」、`V-12` は「この検証が残骸を残さなかったか」を

## 限界（隠さず記録する）

1. **実行器は `dummy` だけである。** 実モデル実行の経路は 1 度も通っていない。
   本検証は「モデルを呼ばずに接続が通る」ことの確認であり、
   「実モデル実行が正しく記録される」ことの確認ではない。
2. **入力 `legacy-source` は代役である。** `verify.py` が実行時に作る `README.md` 1 枚であり、
   実在の旧実装 `chack411/MVC-Music-Store`（`net48`）の作業ツリーは使っていない。
   外側は入力の中身を読まないため接続の確認には足りるが、
   「旧実装の作業ツリーを回収できる」ことの確認ではない。
3. **V-1b は代替評価器でしか確認していない。** 取り違えの 5 検査
   （課題 ID・仕様版・成果物ハッシュ・評価版・成果物パス）が**実評価器で発火する**ことは
   確かめていない。`outer/tests` の `stub_evaluator.py` が返す値に対する確認である。
4. **V-6 の障害は 1 種だけである。** 成果物がビルドできない場合のみ。
   起動のタイムアウト、ポート衝突、データ準備の失敗は宣言した期待として固定していない。
   `V-6` は**成果物の欠陥**を、`V-6b` は**評価側の障害**をそれぞれ 1 種だけ見ている。
5. **使用量は合成である。** `dummy` 実行器が作る使用量記録であり、実モデルの usage の
   揺らぎ（欠落・部分的観測・累積値）は `outer/tests` の単体テストでしか確認していない。
6. **V-7 の `synthetic` は 5 行すべて `true` である。** 実モデル実行の Run が
   集計に混ざった場合の確認はしていない。
7. **環境依存である。** `dotnet` の版とポートの空き状況に依存する。
   `evaluation.json` に `dotnet` の版は記録されないため、別環境での再現は**未確認**である。
8. **V-2 のハッシュ一致は除外規則の差を生まない成果物での結果である。**
   正例には除外拡張子（`.sqlite` など）のファイルが無い。
   除外拡張子を含む成果物で `artifact_sha256` と `artifact_sha256_collected` が
   一致することは確認していない。
9. **V-8 は 1 Run の保存と復元である。** 複数 Run をまとめたパッケージ、
   部分的な破損、復元先の衝突は確認していない。
10. **並列実行・複数課題・中断からの復帰は範囲外である。** 仕様 §1 の非目標であり、
    本検証でも扱っていない。
11. **本検証は 1 環境・1 回の記録である。** 同じ環境で繰り返せば同じ `matched` が得られるが、
    別環境での一致は確認していない。`generated_at` と `dotnet` の版は実行ごとに変わりうる。
12. **V-10・V-12 は Windows のこの機械でのみ確認している。** `V-12` は
    `dotnet.exe` のコマンドラインに `MusicStore.Web.dll` を含むものを探す。
    アプリが別の実行ファイル名で起動される構成や、プロセスを列挙できない環境では
    この検査は成り立たない。`V-10` は正例の評価 1 件の証跡だけを見ている。
13. **V-12 は検証開始時に残骸が無いことを前提にしている。** 開始前に残っていたプロセスは
    差し引くため、**開始前から残っている残骸を検出しない**。
    `V-12` が `[]` であることは「この検証が新たに残さなかった」ことの確認である。
14. **`V-9` は 3 種類の入力でしか確認していない。** 許可リストの名前の綴り違い、
    シンボリックリンク経由の脱出、大文字小文字の違いは確認していない。
15. **`evaluator_sha256` はソースの版ではなく、ビルドした場所と SDK を含む。** 同じソースを
    同じパスで作り直すと同じ値になることは確認した（`bin` `obj` を消して 2 回ビルド）が、
    **同じソースを別のパスに置いてビルドすると値が変わる**ことも確認した
    （[`inner/calibration/README.md`](../../inner/calibration/README.md) §4.1）。
    したがって `V-11` の一致は「外側が呼び出したファイルを実測している」ことの確認であり、
    **別マシン・別パス・別 SDK で同じ値になることの確認ではない**。
    この値の一致を「同じ意味の判定をする評価器である」ことの根拠に使わない。
    **ビルドしたコミットは値に混ぜていない**（同 §4.2）。.NET SDK は既定で作業ツリーのコミットを
    アセンブリに埋め込むため、以前は文書だけのコミットでも値が変わっていた。
    埋め込みを切った今も、**この切り方を知らない別のビルド手順では値が変わりうる**。
    だから固定するときは条件にビルドのコマンドと SDK を書く（§6.4）。
16. **`evaluator_sha256` は、ソースファイルのバイト列にも依存する。** 同じ `.cs` を CRLF で
    保存してビルドすると値が変わる（実測: LF `d6798301…` に対し CRLF `d5443910…`。
    いずれもコミットを値に混ぜる 2 経路を切る前の計測であり、**現在の値ではない**）。
    `.gitattributes` が `eol=lf` なので**チェックアウトしたままの作業ツリー**が基準であり、
    記録に使う値は**追跡ファイルを書き換えていないクリーンな作業ツリー**で測る。
    コミットを混ぜる不具合は直したが、**測り直さずに記録すると、前のように再現しない値を
    残しかねない**。記録を作ったら**その記録コミットの後で作り直して同じ値になることを確かめる**
    （[`inner/calibration/README.md`](../../inner/calibration/README.md) §4.3）。
17. **固定値による採点の拒否は、代替評価器でしか確認していない。** `V-11` で実評価器を
    使っているのは**固定していない**場合であり、`evaluation.evaluator_sha256` に固定値を
    入れたときの経路（`evaluator_build` が欠けたときの拒否、固定値と一致しないビルドの
    `rejected_mismatch` 記録）は `outer/tests` の `stub_evaluator.py` に対する確認である。
    **実評価器を固定値で採点する経路は、この検証では走っていない。**
18. **`V-6b` は代替評価器でしか確認していない。** 実評価器が `exit 2` を返す経路
    （台帳やカタログの読み込み失敗、未実装の検査 ID、成果物ディレクトリの欠落、
    `--work` が空でない、`dotnet` が見つからない）のうち、外側の扱いを確かめているのは
    `outer/tests` の `stub_evaluator.py` の `fault` モードである。
    実評価器の `exit 2` は `inner/calibration` の `fault-missing-artifact`
    `fault-unimplemented-check` で確認しているが、**その成果物を外側が採点する経路は
    走っていない**。`V-6` が実評価器を使っているのは**成果物の欠陥**の場合である。
19. **`V-14` は `V-2` の正例 1 件の成果物でしか確認していない。** `bin` `obj` を
    プロジェクト直下に置く構成（既定の SDK 構成）での確認であり、
    `-p:BaseIntermediateOutputPath` などで出力先を変えた成果物、
    複数プロジェクトを含む成果物、`global.json` で SDK を固定した成果物では確認していない。
    また、この検査は**採点の後に**ファイル一覧を突き合わせるものであり、
    採点の途中で一時的に書かれることを禁じてはいない。
20. **`V-13` は 1 種類の改変でしか確認していない。** 固定後の `frozen/` にある `.cshtml` を
    1 つ書き換えた場合のみ。ファイルの追加・削除、`frozen/` の外（`snapshot.json` や
    `record.json` など）の改変、シンボリックリンクの差し替えは確認していない。
    照合はハッシュのみであり、**ハッシュの一致は成果物の中身の同一性しか示さない**。
